## 1. Executive Summary

Quillva is a two-sided book-review marketplace. Authors list books and pay in a virtual currency ("Quills"); readers apply to review those books and earn Quills back. Quills are bought with real money through Stripe subscriptions and top-up packs. ## 3. Project Overview




**What it does.** Quillva connects self-published authors who need reviews with readers willing to write them, using Quills as the settlement currency.

- **Authors** submit a book (metadata, cover image via Cloudinary, PDF via Firebase Storage). An admin approves it. The author then creates a *listing* specifying distribution channel (free download, KDP purchase, Kindle Unlimited, paperback, audiobook), target countries, number of reviews wanted, and optional video/image review requests. Quills are deducted at listing creation, priced by a rules engine.
- **Readers** browse listings, apply to review, receive a due date (default 7 days), claim a promo code where the channel requires one, and submit a review with a rating and Amazon review URL. On author confirmation, the reviewer is credited Quills.
- **Money** enters via Stripe: three subscription tiers (Basic/Standard/Premium, monthly or yearly) with a free trial, plus five one-off Quill top-up packs. A Stripe customer portal handles plan changes and cancellation.
- **Affiliates** get a referral code and tokenised landing links; clicks and referrals are tracked, and commissions accrue on referred users' paid invoices. Earned balances can be withdrawn through a payout request workflow.
- **Admins** get KPI/trend/breakdown analytics, user and book moderation, a support ticket and dispute desk, broadcast and targeted notifications, CSV exports, editable public page content and injectable site scripts, and a live editor for the Quill pricing rules and Stripe price mappings.

**Who uses it.** Production data shows three populations: 181 reader-role accounts, 9 author-role accounts, and 2 admin accounts. (*Qualification: role alone does not prove active use; the activity log shows 173 distinct users performing at least one audited action.*)

**Process replaced.** This was a rebuild, not a greenfield product (see §2 for how the engagement arose, and §4 for the assessment that justified it). `old-build/` contains the previous Quillva implementation — 22 Prisma models, a Create-React-App frontend mixing MUI, Bootstrap, Flowbite and Framer Motion, Firebase DataConnect, Flutterwave alongside Stripe, and a Telegram bot module. The rebuild consolidates onto one payment provider, one UI system, one ORM and one database. *(Evidence level: VERIFIED that the legacy code exists with those dependencies; INFERRED that consolidation was the motive — no written requirements document was found.)*

## 4. The Legacy System: Technical Assessment

This section is an evidence-based assessment of the system Abraham was asked to review, conducted during this audit against the code preserved in `old-build/`. It exists because the rebuild decision is only defensible if the thing it replaced was genuinely unfit — and that judgement should rest on findings, not on the opinion of the person who replaced it.

**Scope note:** `old-build/` has no git history, so authorship, timeline and whether these defects reached production cannot be established. The findings below are properties of the code as handed over.

### 4.1 The webhook defect — almost certainly the bug that could not be fixed

The legacy Stripe webhook controller shows every symptom of a team stuck on signature verification, and contains the likely root cause plus a second bug that would have actively misled them:

```js
// old-build/backend/src/webhook/webhook.controller.ts
const rawBody = req.rawBody || req.body || req;   // ← root cause
...
event = stripe.webhooks.constructEvent(rawBody, signature, process.env.STRIPE_WEBHOOK_SECRET);
```

**Root cause.** Stripe signature verification requires the *unmodified raw bytes*. The `||` fallback chain means that whenever `req.rawBody` is absent — which is exactly the failure being debugged — the code silently passes the **parsed JSON object**, or even the entire **request object**, into `constructEvent`. Verification then fails 100% of the time, and the fallback guarantees it fails *quietly*, with no indication that the wrong input was supplied. The fallback intended as a safety net is the thing that removes the diagnostic signal.

**The misleading second bug.** Surrounding the call is hand-rolled HMAC debugging — the classic signature of a developer, or an AI assistant, flailing at this problem:

```js
const expectedSignature = crypto.createHmac('sha256', process.env.STRIPE_WEBHOOK_SECRET)
  .update(payload, 'utf8').digest('hex');
console.log('- Signatures match:',
  ('v1=' + expectedSignature) === signature.split('v1=')[1]?.split(',')[0]);
```

The left side has a `v1=` prefix; the right side is the result of splitting *on* `v1=`, so the prefix is already removed. **This comparison can never be true**, even when the signatures match perfectly. Any developer trusting this debug output would conclude their secret or payload was wrong when it may have been correct — which is a highly plausible explanation for why the team, and their AI tooling, could not converge on a fix.

By contrast, the rebuild resolves the whole class of problem in one line in `main.ts`, with no fallback and nothing to mask failure:

```ts
app.use('/stripe/webhook', raw({ type: 'application/json' }));
```

*Evidence level:* **VERIFIED** that both defects exist in the legacy code and that the rebuild handles it correctly. **INFERRED** that this specific defect was the one Abraham was called in to fix — the client-attested description (a bug the team could not resolve even with AI) matches these findings closely, but the engagement predates the new repository's history and no ticket or correspondence was available.

## 5. Business Problem and Context




The marketplace has three problems that make it harder than a CRUD app:

1. **Money and virtual currency must stay reconciled.** Real money buys Quills; Quills buy listings; listings pay out Quills to reviewers; refunds, chargebacks and disputes must reverse the right amount in both directions. Any duplicate webhook delivery that double-credits a balance is a direct financial loss.
2. **The economics change often.** Quill prices vary by word count band, distribution channel, target country, media type, plan, and promotional caps. Hard-coding these would mean a deploy per pricing experiment.
3. **The workflow is time-based, not request-based.** Listings publish on a future date in Amazon's timezone. Review deadlines expire. Trials end. Yearly subscribers must receive monthly Quill tranches. None of this is triggered by a user clicking anything.

## 8. Main Workflows




1. **Author listing lifecycle** — book submitted (cover → Cloudinary signed upload, PDF → Firebase Storage with size validation) → admin approval → listing created with cost from the Quill rules engine → Quills debited → optional future publish date scheduled as a delayed BullMQ job → reviewers apply → reviews submitted → author confirms → reviewer credited → unused capacity refunded on cancellation or deletion.
2. **Reviewer application lifecycle** — browse (filtered by country availability, mutual-review exclusion, already-applied exclusion and caps) → apply → 7-day due date → reminder enqueued to RabbitMQ with a 24-hour TTL → review submitted, or application auto-expired by the 5-minute cron → Quills granted on author confirmation, revoked if the review is later rejected.
3. **Billing lifecycle** — checkout session → subscription created with trial → trial credit granted → `invoice.paid` grants the plan's Quill allocation → `invoice.payment_failed` sets a 7-day `cancel_at` grace window and emails the customer → refunds and disputes reverse Quills, and restore them if a dispute is won.
4. **Affiliate lifecycle** — referral code → tokenised landing link → click recorded with hashed IP and user-agent → signup attributed → commission accrued on referred invoices → payout requested, reviewed and processed.
5. **Support and dispute lifecycle** — ticket raised (general/billing/technical/dispute) → threaded messages with admin read receipts → Stripe dispute records linked to tickets → resolution notes.

## 10. Engineering Implementation Highlights




**Layered Stripe idempotency.** Two independent defences. A `StripeWebhookEvent` table keyed on Stripe's own event ID records every event seen — 462 production rows, 462 distinct IDs. Separately, every balance-changing effect carries a deterministic `idempotencyKey` on the `QuillsTransaction` ledger (`stripe:topup:credit:*`, `stripe:invoice-credit:*`, `stripe:trial-credit:*`, `stripe:refund:topup:*`, `stripe:dispute:topup:*`, `stripe:dispute:topup:restore:*`), with a `@unique` constraint so a replayed effect fails at the database rather than silently double-crediting. The dispute pair is the subtle part: a chargeback debits Quills back out, and a *separate* restore key credits them again if the dispute is later won.

**Raw-body webhook verification.** `app.use('/stripe/webhook', raw(...))` mounts before the global JSON parser so Stripe's signature verifies against unmodified bytes — a common source of silent webhook failure in NestJS.

**Four independent RabbitMQ pipelines.** Review reminders, trial expiry, yearly Quill tranches and application expiry each get their own queue, fanout dead-letter exchange, DLQ, message TTL, prefetch count and per-minute rate limit, all environment-configurable. The reminder TTL defaults to 24 hours to match the one-day lead time, so an undeliverable message expires rather than arriving late.

**Consumer-level idempotency via compare-and-set.** Rather than trusting the queue, the reminder consumer runs `updateMany({ where: { id, reminderSent: false }, data: { reminderSent: true } })` and sends only if `count === 1`. Any duplicate delivery from any worker loses the race and acks silently. The same pattern guards trial reminders and yearly tranches. A sliding-window rate limiter (timestamp array pruned to 60 seconds, 250 ms backoff) protects the SMTP provider during bursts without dropping messages.

**Timezone-aware delayed publication.** Future-dated listings convert from `America/New_York` (Amazon's publishing zone) to UTC with Luxon, then enqueue as a BullMQ delayed job with a deterministic `jobId` of `listing-<id>` so rescheduling replaces rather than duplicates.

**Configuration as data.** The `QuillRule` table holds 91 live rules across 15 categories — word-count bands, per-channel and per-country costs, media surcharges, plan allocations, top-up packs, listing/reviewer/weekly caps, exchange rate and welcome bonus. `BillingPriceMapping` (shipped 2026-10-04) does the same for Stripe price IDs, but with validity windows (`validFrom`/`validTo`), an `isActive` flag and a `quillsSnapshot`, bootstrapped idempotently in Render's `preDeployCommand`. 17 mappings exist, 11 active — the rest are superseded historical prices retained deliberately.

**Audit trail, soft deletes, media lifecycle.** An interceptor records every mutating call with request signature, `x-user-action` description, entity, entity ID, JSON metadata and IP — 21,825 rows with 100% coverage across 15 entity types. Six models soft-delete; because a soft-deleted user must not block re-registration, the unique constraint is the composite `[email, deletedAt]`. Cloudinary uploads are signed server-side, registered as `TempMedia` with status `TEMP`, and flipped to `ATTACHED` on save, leaving orphans identifiable (92 attached, 6 orphaned in production).

#### Correction notice — and why the earlier reading was wrong

An earlier version of this dossier concluded there were **no** paying customers. That was wrong, and the reason is worth recording because it is a genuine analytical lesson.

The reasoning was: *no `stripe:invoice-credit:*` entries exist in the Quills ledger, therefore no paid invoice was ever processed.* The flaw is in the pricing configuration:

```
QuillRule | SUBSCRIPTION | BASIC | value = 0   ("Monthly quills for BASIC plan")
```

**The BASIC plan grants zero monthly Quills by design.** Every paying subscriber is on BASIC. The code therefore correctly creates no credit ledger entry for a paid BASIC invoice — so the ledger's silence reflects the *plan's economics*, not the *absence of payment*. `SubscriptionHistory.quillsAllocation = 0` across all 44 rows has the same innocent explanation.

The lesson: **absence of a derived record is not absence of the source event**, unless you have first confirmed that the source event is supposed to produce that record. The chargebacks were the disconfirming evidence available all along — a chargeback cannot exist without a charge.

*Separately resolved: every user's balance carries 10,000 Quills that the ledger does not explain. This is the `WELCOME_BONUS` rule (10,000 Quills for new users), granted as a direct balance rather than a ledger entry. Not a defect, but the welcome bonus is the one balance-changing event in the system that is not auditable from `QuillsTransaction` — see §25.*

## 13. Significant Engineering Challenges




Four constraints made this harder than a CRUD application, and each is detailed above or below rather than repeated here:

- **Money that flows backwards.** A Quill balance has to survive refunds, chargebacks and chargeback reversals arriving out of order and months apart. One idempotency key is not enough, because a replayed *event* and a re-derived *effect* are different failures (§10, §18 Claim 3).
- **Duplicate execution across replicas.** `TODOS.md` states the trade-off explicitly: cron inside the API means every replica runs every job. Resolved by extracting a separate worker service *and* making every job idempotent at the row level, so correctness never depended on there being exactly one worker (§14).
- **Cross-site cookie auth behind a proxy chain.** `SameSite`, `Secure`, cookie `domain` and Express `trust proxy` interact, the stack is Netlify → Cloudflare → NGINX → Render, and the failure mode is a silent 401 with no server-side error (§15.1).
- **Timezone correctness for a third party's clock.** Listings publish on Amazon's schedule, not the server's or the user's — and the failure mode is only ever "it went live late" (§15.2).

## 14. Architectural Decisions and Trade-offs




**Decision: dedicated worker process rather than cron inside the API.**
*Problem* — cron in the API couples job execution to HTTP deployment and duplicates jobs per replica. *Decision* — extract `worker.ts`/`worker.module.ts`, deploy as a separate Render worker from the same Docker image, gated by `LISTING_SCHEDULER_WORKER`. *Reasoning* — written out in `TODOS.md`. *Trade-off* — a second service to deploy, monitor and pay for; shared image means a backend deploy redeploys both. *Result* — API restarts no longer pause background work, and scaling the API no longer risks duplicate job execution.

**Decision: RabbitMQ for scheduled notifications, BullMQ for delayed publication.**
*Problem* — two different temporal needs. *Decision* — RabbitMQ with DLX/TTL for fan-out reminder workloads; BullMQ (Redis) delayed jobs with deterministic job IDs for single future-dated publications. *Trade-off* — two brokers to run and reason about, which is unusual for a system this size. *Reasoning (INFERRED from code shape)* — BullMQ's `jobId` + `delay` makes reschedule-by-replace trivial, which RabbitMQ does not; RabbitMQ's DLX/TTL makes expiring stale reminders trivial, which BullMQ does less naturally. *Result* — both work, at the cost of operational surface area.

**Decision: pricing rules in the database, not in code.**
*Problem* — 15 categories of pricing input, changed frequently. *Decision* — a `QuillRule` table with category/key/min/max/value, read at estimate time. *Trade-off* — pricing logic is no longer type-checked or reviewable in a PR, and a bad admin edit is a production incident with no rollback. *Result* — 91 live rules; economics change without deploys.

**Decision: Stripe price IDs in the database, not environment variables.**
*Problem* — env-var price IDs mean a redeploy to add a pack and no history of what a past subscriber actually paid. *Decision* (2026-10-04) — `BillingPriceMapping` with `validFrom`/`validTo`, `isActive` and a `quillsSnapshot`, bootstrapped idempotently from env on each deploy. *Trade-off* — one more source of truth to keep in sync with the Stripe dashboard. *Result* — 17 mappings, 11 active; superseded prices retained rather than overwritten.

**Decision: grace period instead of immediate revocation on payment failure.**
*Problem* — a failed invoice originally cut access immediately, punishing users whose card merely expired. *Decision* (2026-08-02) — set Stripe `cancel_at` to now + 7 days and email the customer, letting Stripe's dunning retries run. *Trade-off* — up to 7 days of unpaid access. *Result* — 101 `invoice.payment_failed` events in production handled this way rather than as 101 instant lockouts.

**Decision: soft deletes throughout.**
*Trade-off* — every query must filter `deletedAt: null`, which is easy to forget, and the unique email constraint had to become composite. *Result* — financial and review history survives account deletion, which the ledger requires.

## 15. Problems Solved



**15.1 Cross-site cookie authentication failing in production.** SPA on Netlify, API on Render behind Cloudflare and NGINX; authentication succeeded but every subsequent request returned 401, with no local reproduction available. Diagnosed by adding token-generation logging and bisecting the `SameSite`/`Secure`/`domain`/`trust proxy` matrix across 14 small deployable increments on 2026-01-24, converging on Express `trust proxy` enabled for the proxy chain, no forced cookie domain, and a minimal JWT payload. *Result:* cookie auth works cross-origin; `GET /auth/me` appears 3,488 times in subsequent production logs. *Evidence:* git log 2026-01-24; `ActivityLog` endpoint counts.

**15.2 Listings publishing three hours late.** Scheduled publication converted from `America/Los_Angeles` instead of Amazon's `America/New_York`, shifting every future-dated listing. Fixed the Luxon zone in `toUtcFromAmazonTz` and made the method public so the update path reused it rather than re-deriving the conversion. *Evidence:* commit 2026-02-02.

**15.3 Duplicate accounts from case-sensitive email matching.** Users registering with differently-cased emails got separate accounts, splitting Quill balances and Stripe customer records. Wrote an audit script that reference-counts each duplicate across direct relations, owned content and hard foreign keys to produce a "signal score" and a `safeAutoDelete` verdict; shipped a dry-run-by-default cleanup script (`--apply` to commit), a separate merge script with a reviewed plan per affected pair, and an email case-insensitivity fix at the source. *Result:* **zero** duplicate case-insensitive emails among non-deleted users as of 2026-10-15. *Evidence:* commit 2026-08-02; `prisma/scripts/`; production query.

**15.4 One-time passcodes leaking in API responses.** The OTP flow returned the generated code in the HTTP response, so anyone able to trigger an OTP could read it without inbox access, defeating the second factor. Removed OTP fields from backend responses and frontend auth types in a coordinated change. *Evidence:* paired commits dated 2026-10-04 in both repositories.

**15.5 Shared notification read state.** Broadcast notifications used a single `read` boolean on the notification row, so the first recipient to open one marked it read for everyone. Introduced a `NotificationRead` join table with a `[notificationId, userId]` unique constraint and scoped admin notification views by default. *Evidence:* commits 2026-10-04.

**15.6 Subscription Quill allocations lost on plan changes.** Plan and interval switching interacts with pending-plan state and Quill grants. Resolved with explicit pending-plan and pending-interval fields, a `yearlyQuillsEnqueued` guard, and hourly tranche delivery for annual subscribers. *Evidence:* schema fields, cron service, commit `Preserve subscription quill allocations` (2026-10-04). *The exact failure mode before the fix is not recorded — INFERRED.*

## 16. Security, Reliability and Operational Considerations




**Present and verified:** bcrypt password hashing; JWT in httpOnly cookies with a minimal payload; OTP-gated login with password reset and account restore; role-based access (READER/AUTHOR/ADMIN); explicit CORS allow-list; global `ValidationPipe` with DTO validation on every endpoint; `ClassSerializerInterceptor` with `excludeExtraneousValues` so entities cannot leak unexposed fields; Stripe signature verification against raw bytes; webhook event-ID deduplication; unique idempotency keys on financial ledger rows; upload size limits for PDFs and covers; hashed IP and user-agent on affiliate click tracking (privacy-conscious attribution); Redis locked to internal network access only; a full per-action audit log with IP capture; account suspension/reactivation with email notification; dead-letter queues and TTLs on every RabbitMQ pipeline; boot-time catch-up scans gated behind explicit flags; Docker multi-stage builds that exclude dev dependencies from the runtime image; and a written production launch checklist for the billing cutover.

**Gaps — stated plainly, and worth being honest about in interviews:**
- **Test coverage is thin.** 35 spec files exist, but only `webhook.service.spec.ts` (6 tests) and `stripe.service.spec.ts` (3 tests) contain real assertions — and notably these are the *right* two files to have covered, since they guard the money. The other 33 are unmodified NestJS "should be defined" scaffolds. **Do not claim a tested codebase; claim targeted test coverage of the financial paths.**
- **No CI/CD pipeline.** No `.github/workflows`, CircleCI, GitLab CI or equivalent in any repository. Deployment is Render's build-on-push with a `preDeployCommand` running migrations and seeds.
- **No APM or error tracking.** No Sentry, Datadog, New Relic or OpenTelemetry integration; observability is NestJS `Logger` output plus the `ActivityLog` table.
- **`prisma db seed` runs in the production pre-deploy command**, which is unusual and depends on the seed being strictly idempotent.
- **No leader election.** Correctness under multiple workers rests entirely on row-level compare-and-set, which is sound but undocumented as a guarantee.

## 17. Lessons Learned

- **Go to the failing call, not the error message.** The legacy webhook bug was invisible from its symptoms and obvious at the `constructEvent` call site. A team and its AI tooling spent far longer than necessary because they debugged outward from the error rather than inward to the input.
- **Never trust debug output you did not write.** The legacy signature comparison could never return true. Fabricated certainty is worse than no information, and it is the first thing to verify when a diagnosis will not converge.
- **A fallback that hides a failure is worse than the failure.** `req.rawBody || req.body || req` was written as a safety net and worked as a blindfold. Defaults belong where the fallback is genuinely valid, never where it masks the condition being diagnosed.



- **Idempotency belongs in the database, not the queue.** Every guarantee that actually held in production — webhook dedup, reminder send-once, trial credit — is a unique constraint or a conditional update. Queue configuration (TTL, DLX, prefetch) limited the blast radius but never provided the guarantee.
- **Two independent dedup layers are not redundancy.** Event-level and effect-level keys catch genuinely different failures. The dispute-restore case proves it: the same Stripe event can legitimately produce two opposite ledger effects.
- **Empirical debugging is the right tool for opaque infrastructure.** The 14-commit cookie sequence looks untidy in a git log, but `SameSite`/`Secure`/`domain`/`trust proxy` behind a CDN has no local reproduction; shipping small changes with logging was faster than reasoning about it.
- **Configuration that the business changes often should live in the database** — but the 2026-10-04 Stripe mapping work shows the second half of the lesson: it also needs validity windows and snapshots, or you lose the history of what customers actually paid.
- **Invest test coverage where money moves.** With limited time, nine real tests concentrated on the Stripe webhook and service was the correct allocation — but leaving 33 scaffold specs in place is misleading to anyone reading the repository, and deleting them would have been more honest than keeping them.
- **Separating the worker was right; doing it earlier would have been better.** The coupling and duplicate-execution risks were written down in `TODOS.md` before they were fixed, which means they were understood and deferred rather than missed.
- **What I would do differently:** add CI running lint, build and the Stripe tests on every push; add Sentry before launch rather than relying on the audit log for incident reconstruction; replace `prisma db seed` in pre-deploy with an explicit, separately-triggered migration step; and pick one broker rather than running both RabbitMQ and BullMQ for a system of this size.

## 21. Interview Story Bank

**The rescue — fixing what a team plus AI could not.** *S:* A long-standing client's platform, built by another team, had a Stripe webhook that would not verify signatures. The team had been stuck for some time and AI tooling had not resolved it; the client called me in. *T:* Diagnose a payment defect in a codebase I had never seen, under a client who had already lost confidence in the delivery. *A:* Went to the signature-verification call first rather than the symptom. Found a fallback chain — `req.rawBody || req.body || req` — that silently passed parsed JSON into `constructEvent` whenever the raw body was missing, guaranteeing failure *and* suppressing the diagnostic signal. Then found a second bug in their own debug logging: a signature comparison that prefixed `v1=` onto one side while splitting it off the other, so it could never return true. That false negative is almost certainly why they and their AI tools kept chasing the secret and the payload instead of the input. *R:* Fixed within a few hours of first touching the code. *E:* Both defects are still present in `old-build/backend/src/webhook/webhook.controller.ts`; the rebuild replaces the whole class of problem with one unambiguous line of raw-body middleware. *Why I tell it:* it is a story about reading the failing call rather than the error message, and about not trusting debug output you did not write.

**Saying no to a launch — technical judgement against commercial pressure.** *S:* After the fix, the client asked whether the platform was ready to go live. The easy, profitable answer was yes. *T:* Give an honest production-readiness assessment. *A:* Reviewed authentication, the payment path and the frontend. Found no webhook idempotency anywhere — a replayed Stripe event would re-credit a subscription — plus `origin: '*'` CORS with a comment admitting it was insecure, the webhook secret being logged on every failure, six overlapping UI libraries, two state management libraries, two payment providers, and no type safety or meaningful tests. *A (cont.):* Advised against launch and proposed a rebuild, making the financial risk legible to a non-technical owner rather than listing code smells. *R:* The client accepted; the rebuild shipped and went live in June 2026. *E:* Every defect is verifiable in `old-build/` (§4.2). *What I'd add:* the rebuild was the proportionate call, not the ambitious one — a codebase with that many competing foundations is not cheaper to remediate than to replace.

**Debugging under opacity — the cookie that wouldn't stick.** *S:* SPA on Netlify, API on Render behind Cloudflare/NGINX; auth succeeded, every subsequent request 401'd. *T:* make httpOnly cookie auth work cross-origin with no local reproduction. *A:* added token-generation logging, then bisected the `SameSite`/`Secure`/`domain`/`trust proxy` matrix in small deployable increments over one day. *R:* auth worked; 3,488 `GET /auth/me` calls follow in production logs. *E:* 14 commits dated 2026-01-24. *The point I'd make:* the git log looks messy and that was the right trade-off — measuring beat reasoning in the abstract about CDN cookie behaviour.

**Correctness under replay — the chargeback that had to reverse twice.** *S:* Stripe can deliver the same event twice, out of order, months apart; a duplicate credit is real money lost. *T:* make the ledger provably correct under replay. *A:* two independent layers — an event-ID dedup table, plus deterministic unique idempotency keys per ledger effect, with *separate* keys for a dispute's debit and its restore-on-win. *R:* 462 events, 462 distinct IDs, no double-credit. *E:* `webhook.service.ts`; schema constraint; production query.

**Ownership and documented trade-offs — the worker that should have been separate sooner.** *S:* cron and BullMQ ran inside the API, so every replica would duplicate every job. *A:* wrote the trade-off into `TODOS.md` with an explicit trigger ("if you scale to 2+ instances, extract the worker or add leader election"), shipped features, then extracted `worker.ts` as its own Render service when the risk became real — and made every job row-level idempotent so correctness never depended on the extraction. *E:* `TODOS.md`; commit 2026-01-24; `render.yaml`.

**Production data incident — the duplicate accounts.** *S:* case-sensitive email matching split Quill balances and Stripe customers across duplicate accounts. *T:* fix the cause and repair live data without destroying anything. *A:* reference-count scoring to decide what was safe to delete, dry-run by default with an explicit `--apply`, a separate merge script with a reviewed plan per pair, and a source-level fix. *R:* zero duplicates among active users. *E:* `prisma/scripts/`; commit 2026-08-02.

**Judgement about scope — where to spend limited testing time.** *S:* solo engineer, broad surface, limited time. *A:* wrote real tests only for the Stripe service and webhook service — refund reversal, dispute debit, dispute restore. *R:* the money paths are covered; the rest is not. *What I'd say:* I'd defend the allocation and criticise the execution — leaving 33 "should be defined" scaffolds misrepresents coverage, and deleting them would have been the honest move.

**Improving an existing system — pricing out of code.** *S:* Quill pricing depended on word count, channel, country, media and caps, and changed often. *A:* moved it into a rules table read at estimate time; later did the same for Stripe price IDs, but with validity windows and value snapshots after learning that overwriting a price loses the record of what past customers paid. *R:* 91 rules and 17 mappings live, changeable without a deploy. *Trade-off I'd raise unprompted:* pricing logic is no longer type-checked or PR-reviewed, and a bad admin edit is an incident with no rollback.
